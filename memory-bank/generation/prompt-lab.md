# Prompt Lab

Core internal CLI tool for side-by-side BFL Flux 2 prompt tuning. Every new demo/tenant photo goes through the lab to find wording that renders consistently.

**Script**: `scripts/prompt-lab.ts`
**Sessions**: `tmp/prompt-lab/<session>/` (persists across days, gitignored)

## Why

Flux 2 is sensitive to exact wording. Small changes in action clauses produce visibly different results. The old workflow — edit prompt, generate one image, look, repeat — was serial and untrackable. The lab lets you fire N prompt variations in parallel, compare side by side, and track what worked across sessions.

## Commands

```bash
prompt-lab ls                              # List all sessions
prompt-lab init <session> --photo <id>     # Create session from DB step_photo UUID
prompt-lab status <session>                # Show variants, runs, verdicts, action clauses
prompt-lab add <session> --from <id> --id <new> --label "..."
                                           # Fork a variant (deep-copies prose)
  [--model flux-2-pro]                     #   Override BFL model
  [--scoped subcatId:optionId]             #   Single-surface scoped edit instead of full gen
  [--refine "prompt"]                      #   Add a second Max pass (oven correction etc.)
  [--refine-swatch subcatId]               #   Pass swatch as reference image to refine pass
prompt-lab show <session>                  # Print assembled prompts (no BFL call, free)
prompt-lab run <session>                   # Generate images for all pending variants
  [--concurrency N]                        #   Parallel BFL calls (default 2)
  [--variant <id>]                         #   Only run one variant
  [--only-pending]                         #   Skip already-completed runs
prompt-lab review <session>                # Build HTML comparison page and open it
prompt-lab apply <session>                 # Write approved variant's prose to DB
  [--variant <id>]                         #   Specify which (default: the one marked approved)
prompt-lab import-verdicts <session> --file <path.json>
                                           # Import exported decisions back into config
```

## Session Structure

```
tmp/prompt-lab/<session>/
  config.json       # Photo, selections, variants, results, verdicts
  source.jpg        # Downloaded source photo (from Supabase `rooms` bucket)
  results/          # Generated images
    baseline-0.jpg
    v2-0.jpg
    v2-1.jpg
    v3-0-pre-refine.jpg   # Pre-refine image (when refine pass is used)
    v3-0.jpg              # Final post-refine image
  review.html       # HTML comparison page (regenerated by `review` command)
```

## Workflow

1. **Init**: `prompt-lab init valor-kitchen --photo <UUID>` — downloads photo, pulls default selections (is_default options for scoped subcategories), saves current DB prose as the "baseline" variant.

2. **Add variants**: Fork from baseline and edit the prose in `config.json`:
   ```bash
   prompt-lab add valor-kitchen --from baseline --id v2 --label "shorter cab clause"
   ```
   Then edit `tmp/prompt-lab/valor-kitchen/config.json` — change the action clauses in the new variant's `prose.actions` object. Set `runs: 3` to test consistency.

3. **Preview** (free): `prompt-lab show valor-kitchen` — prints the assembled prompt for each variant without calling BFL.

4. **Run**: `prompt-lab run valor-kitchen --concurrency 3` — fires all pending variants to BFL in parallel.

5. **Review**: `prompt-lab review valor-kitchen` — generates an HTML page with side-by-side results. Source photo on the left, variant columns with generated images, prompt text, approve/reject/maybe buttons, notes per variant. Click to zoom. Verdicts stored in localStorage + exportable as JSON.

6. **Iterate**: Add more variants, re-run, re-review. `--only-pending` skips completed runs.

7. **Ship**: `prompt-lab apply valor-kitchen` — writes the approved variant's prose to `step_photos.prompt_prose` in the DB.

## Three Generation Modes

| Mode | Config field | What it does | Default model |
|------|-------------|--------------|---------------|
| Full gen | (none) | `buildProsePrompt` → all surfaces | flux-2-max |
| Scoped edit | `scoped: { subcategoryId, optionId }` | `buildProseScopedEdit` → single surface | flux-2-flex |
| + Refine | `refine: { prompt, swatchSubId? }` | Second Max pass on main output | flux-2-max |

`model` field on any variant overrides the default. Refine always uses Max.

When refine is used, both images are saved: `v1-0.jpg` (post-refine) and `v1-0-pre-refine.jpg` (pre-refine) for comparison.

```json
{
  "id": "v2",
  "label": "shorter cab clause",
  "prose": {
    "version": 2,
    "actions": {
      "kitchen-cabinet-color": "apply {image} to every cabinet door and drawer",
      "counter-top": "apply {image} to all countertop surfaces",
      "backsplash": "apply {image} to the backsplash behind each counter section"
    },
    "lead": "Apply the following finishes to this kitchen photo:",
    "style": "Photorealistic real estate photography, natural daylight, neutral white balance."
  },
  "runs": 3,
  "model": "flux-2-max",
  "scoped": null,
  "refine": null,
  "results": [],
  "verdict": null,
  "notes": null
}
```

## Technical Details

- **Calls BFL directly** via `generateImage()` from `src/lib/bfl.ts` — no Inngest, no DB writes during generation. 3-minute poll timeout.
- **Bypasses Next.js `unstable_cache`** — uses `getOptionLookupDirect()` (inline Supabase query) since `unstable_cache` requires the Next.js runtime.
- **Pre-warms swatch cache once** — downloads + downscales all swatch images at the start of a run, shares across all variant jobs.
- **Concurrency-limited** — configurable parallelism for BFL calls (default 2). No rate limit issues observed up to 5.
- **Cost**: ~$0.04/generation (Max), ~$0.01 (Flex/Klein). A typical session with 5 variants × 2 runs = ~$0.40.

## Selections

`init` pulls default selections automatically (is_default options for each subcategory scoped to the photo). Override with `--selections '{"sub":"opt"}'` or edit `config.json` after init. Selections are held constant across all variants in a session — only the prose varies.

## Verdicts

The HTML review page stores approve/reject/maybe + notes in browser localStorage. Export with the "Export Decisions" button → JSON file. Import back into config with `import-verdicts` command. `apply` uses the verdict from config (not localStorage) to determine which prose to write to DB.
